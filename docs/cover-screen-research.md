# Что полезного добавить на внешний экран MIX Flip без root

Исследование от 3 октября 2026 года. Цель — полезные карточки рядом с питомцем/фото, пока телефон раскрыт. В сложенном состоянии сохраняются штатные интерфейс Xiaomi и AOD. Ни одна из функций ниже ещё не объявляется проверенной на HyperOS: это оценка официальных API и текущего кода.

## На чём можно строить

На устройстве уже подтверждены обе включённые панели через shell-режим `OPENED_PRESENTATION`, возврат после складывания, аппаратное декодирование и импорт собственного фото. Это результаты общей работы команды, а не новые проверки в рамках этого research. Android 16, приложение minSdk 29 / targetSdk 35.

У Xiaomi указаны внешний экран 4,01 дюйма и разрешение 1392×1208. Фактическое окно в текущей ориентации телефона — 1208×1392; это не ошибка разрешения. Карточки нужно размещать по текущим размерам окна и безопасной области камеры, используя `SceneGeometry`/insets. Кнопки минимум 48 dp; два-три элемента управления на карточку. [Xiaomi MIX Flip Specs](https://www.mi.com/global/product/xiaomi-mix-flip/specs/).

В коде уже есть `PetNotifications`: подписка на активные медиасессии, состояние проигрывания и сигнал новых уведомлений; `Pets.battery()` читает батарею. Manifest пока не содержит INTERNET, ACCESS_NETWORK_STATE, Bluetooth, календарных или alarm-разрешений. `ControllerService` допускает только три операции: supervise, disable, status. Для карточек не нужен произвольный shell-доступ.

Shizuku с UID 2000 даёт права Android shell, а не root: права и SELinux остаются ограниченными. UserService не является обычным Android application process; системные наблюдатели лучше держать в приложении, а не переносить `registerReceiver` в этот процесс. После перезагрузки rootless Shizuku требуется запустить снова. Это влияет на включение двух панелей, но не обязывает все карточки зависеть от Shizuku. [Shizuku API](https://github.com/RikkaApps/Shizuku-API), [инструкция запуска](https://shizuku.rikka.app/guide/setup/).

## Приоритеты

Сложность относительная: S — небольшой изолированный блок, M — несколько связанных состояний/экранов. Расход — ожидаемый режим обновления; конкретные проценты CPU нужно измерить отдельно на телефоне.

| Функция | Rootless механизм / доступ | Сложность | Обновление и ограничения |
|---|---|---|---|
| 1. Батарея и заряд | ACTION_BATTERY_CHANGED; BatteryManager; специальных runtime-разрешений нет | S | По событиям, почти статичная карточка. Температура именно батареи |
| 2. Музыка / подкаст | MediaSessionManager + MediaController; уже включённый доступ к уведомлениям | S–M | Metadata/playback callbacks; прогресс максимум раз в секунду только при видимости |
| 3. Секундомер / фокус | SystemClock.elapsedRealtime; prefs; для надёжного сигнала в фоне нужен AlarmManager и соответствующий доступ | M | Цифры раз в секунду только при видимости, без постоянной службы для счёта |
| 4. Уведомления без текста | NotificationListenerService, уже существующий доступ | M | По событиям; иконки/количество активных уведомлений, список разрешённых приложений |
| 5. Сеть и наушники | ConnectivityManager + ACCESS_NETWORK_STATE; BluetoothProfile + runtime BLUETOOTH_CONNECT | M | По callbacks/broadcasts; без сканирования эфира. VPN — для сети, доступной нашему приложению |
| 6. Следующий будильник / встреча | AlarmManager.getNextAlarmClock; календарь отдельно через READ_CALENDAR | S для будильника, M для календаря | По изменению + редкое обновление; календарные данные только по opt-in |
| 7. Фото / короткая заметка / QR-карточка | Локальные private-файлы и текст; существующий импорт фото | S | Полностью статично; QR вводится пользователем, без чтения буфера в фоне |
| 8. Погода по выбранному городу | Опциональный HTTPS к Open-Meteo, INTERNET; город/координаты вручную | M | Кэш, обновление на открытии не чаще 30–60 минут; без постоянной геолокации |

## Как конкретно реализовать

### 1. Заряд и температура

Показывать процент, тип питания USB/AC/wireless, статус «заряжается / заряд завершён», температуру батареи. Для первого варианта достаточно уже используемого sticky battery broadcast. Никакой поминутный shell `dumpsys battery` не нужен. [Android: Battery monitoring](https://developer.android.com/training/monitoring-device-state/battery-monitoring), [BatteryManager](https://developer.android.com/reference/android/os/BatteryManager.html).

Оценка скорости зарядки по `BATTERY_PROPERTY_CURRENT_NOW` — отдельная необязательная опция. HAL может не предоставить значение; это ток батареи, а не мощность адаптера. Не показывать «67 W» на основании одного тока/напряжения батареи. Не считать температуру батареи температурой CPU. Возможный удобный штрих — один короткий жест питомца при подключении кабеля, затем обычный спокойный кадр.

`PowerManager.addThermalStatusListener()` доступен с API29 для уровня теплового ограничения. Его можно использовать внутри приложения для снижения частоты анимации при нагреве; в интерфейсе — только если пользователю нужен индикатор. Это не градусы. [PowerManager](https://developer.android.com/reference/android/os/PowerManager#addThermalStatusListener(android.os.PowerManager.OnThermalStatusChangedListener)).

### 2. Медиакарточка

Обложка с ограниченным размером, название, исполнитель, play/pause, next; предыдущий трек при раскрытии карточки. Активный `NotificationListenerService` позволяет получить чужие опубликованные медиасессии без системного MEDIA_CONTENT_CONTROL. Уже имеющийся `PetNotifications` — естественная точка расширения. [MediaSessionManager](https://developer.android.com/reference/android/media/session/MediaSessionManager).

Команды отправлять через `MediaController.TransportControls`, а доступные кнопки определять по `PlaybackState.getActions()`. Это запрос плееру: приложение может не поддержать next/seek или не опубликовать медиасессию. Поэтому нельзя обещать поддержку каждого видеоплеера/браузера. Не проигрывать собственную аудиодорожку и не занимать audio focus. [TransportControls](https://developer.android.com/reference/android/media/session/MediaController.TransportControls).

В проектной реализации выбрать играющую сессию, иначе последнюю подходящую; сохранить предпочтение пользователя при нескольких плеерах. Metadata не писать в диагностический журнал. Выход из сессии очищает карточку. Прогресс считать из последнего PlaybackState локально, без постоянного Binder polling; на паузе обновление прекратить.

### 3. Фокус, таймер и секундомер

Первый простой режим: видимый секундомер и 5/25/50 минут фокуса, пауза/сброс. Основа счёта — монотонный `elapsedRealtime`, который учитывает сон. Handler нужен только для отображения. Сохранять старт/накопленное время и номер загрузки, а не ежесекундно записывать prefs. После закрытия панели считать время при следующем открытии. После перезагрузки монотонную отметку нельзя использовать как прежнюю: восстановить явно выбранную политику, например приостановить сессию и показать сохранённое время. [SystemClock](https://developer.android.com/reference/android/os/SystemClock#elapsedRealtime()).

Для сигнала точно в момент окончания, даже при закрытой панели/убитом процессе, нужен PendingIntent alarm. `SCHEDULE_EXACT_ALARM` — специальный доступ, не гарантирован на свежей установке; проверять `canScheduleExactAlarms()`. Нужны также receiver и канал, а для обычного уведомления на Android13+ — POST_NOTIFICATIONS. Не маскировать отсутствие доступа обещанием точного сигнала. Вариант с OnAlarmListener без специального доступа не решает сохранность при смерти процесса. AlarmManager нужен для одного дедлайна, а не каждого тика. [Android: alarms](https://developer.android.com/develop/background-work/services/alarms).

### 4. Приватные уведомления

По умолчанию только иконки выбранных приложений и количество активных уведомлений. Это не число непрочитанных сообщений: приложение может группировать, переиспользовать или вообще не публиковать уведомления. Учитывать posted/removed, после подключения listener восстановить snapshot через `getActiveNotifications()`; не складывать бесконечный счётчик событий. Обрабатывать group summaries, ongoing и собственные уведомления. [NotificationListenerService](https://developer.android.com/reference/android/service/notification/NotificationListenerService).

Текст/имя отправителя — отдельная явная настройка. При блокировке дисплей нашей панели уже закрывается; дополнительно очищать приватный snapshot. Android15+ скрывает OTP от недоверенных notification listeners: доступ к уведомлениям не даёт права читать каждый код. Обход этой защиты не нужен. [Android 15: OTP redaction](https://developer.android.com/about/versions/15/behavior-changes-all#otp-redaction).

Не предлагать автоматическую отправку ответов. Нажатие иконки может открыть исходное приложение на основном экране, но маршрутизация PendingIntent на Display0 требует отдельной проверки HyperOS: наличие `ActivityOptions.setLaunchDisplayId()` само по себе не гарантирует, что чужая activity разрешена на нужной панели. [ActivityOptions](https://developer.android.com/reference/android/app/ActivityOptions#setLaunchDisplayId(int)).

### 5. Wi-Fi, интернет, VPN и Bluetooth

Небольшая строка «Wi-Fi / мобильная сеть / нет подтверждённого интернета», VPN и название подключённых наушников. NetworkCallback даёт изменения транспортов/VALIDATED без периодического shell. ACCESS_NETWORK_STATE — normal permission. VPN обозначает транспорт сети нашего приложения: это не аудит VPN всего устройства и не обещание, что весь трафик защищён. SSID не нужен первой версии; его чтение связано с дополнительными ограничениями чувствительных данных. [Android: network state](https://developer.android.com/develop/connectivity/network-ops/reading-network-state).

Для уже подключённых Bluetooth-профилей нужен runtime BLUETOOTH_CONNECT, а не BLUETOOTH_SCAN. Bonded devices — сопряжённые, а не обязательно подключённые; состояние читать через профиль A2DP/HEADSET и его события. Заряд любых наушников через общий публичный API не обещать: отдельные устройства дают его через свои протоколы/приложения. [Bluetooth permissions](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions), [BluetoothProfile](https://developer.android.com/reference/android/bluetooth/BluetoothProfile).

Прямые `WifiManager.setWifiEnabled()` для target29+ и `BluetoothAdapter.enable/disable()` для target33+ не подходят обычному приложению. Первая версия открывает системные панели/настройки на основном экране. Дополнительные Shizuku-переключатели можно изучить позже отдельно для этого телефона. [WifiManager](https://developer.android.com/reference/android/net/wifi/WifiManager#setWifiEnabled(boolean)), [Android 13 Bluetooth changes](https://developer.android.com/about/versions/13/behavior-changes-13#bluetooth-adapter), [Settings.Panel](https://developer.android.com/reference/android/provider/Settings.Panel).

Важный нюанс Android16: `TetheringManager` стал публичным в API36; event callback требует ACCESS_NETWORK_STATE. Для статуса использовать публичный `TetheringEventCallback.onTetheredInterfacesChanged(Set<TetheringInterface>)` и `getType()==TETHERING_WIFI`: это лучше, чем угадывать по наличию upstream. Документация регистрации упоминает upstream, но callback-страница API36 показывает именно интерфейсы. Null upstream сам по себе не доказывает выключение hotspot. [Публичный callback API36](https://developer.android.com/reference/android/net/TetheringManager.TetheringEventCallback), [TetheringInterface](https://developer.android.com/reference/android/net/TetheringInterface). Управление обычной точкой доступа/список клиентов пока эксперимент: документация `setSoftApConfiguration` содержит TETHER_PRIVILEGED, а публичная поверхность и доступность отличаются по версиям. `startLocalOnlyHotspot` создаёт локальную сеть без интернета и не является заменой пользовательской раздачи интернета. На HyperOS это ещё не проверено. [TetheringManager](https://developer.android.com/reference/android/net/TetheringManager), [TetheringRequest.Builder](https://developer.android.com/reference/android/net/TetheringManager.TetheringRequest.Builder), [LocalOnlyHotspot](https://developer.android.com/reference/android/net/wifi/WifiManager#startLocalOnlyHotspot(android.net.wifi.WifiManager.LocalOnlyHotspotCallback,android.os.Handler)).

### 6. Следующий будильник и календарь

«Будильник завтра 07:30» через `getNextAlarmClock()`, без чтения БД Xiaomi Clock. Он возвращает только будильники, опубликованные приложениями соответствующим системным способом; отсутствие значения — нормальное состояние. Не читать private data других приложений. [AlarmManager](https://developer.android.com/reference/android/app/AlarmManager#getNextAlarmClock()).

«Следующая встреча через 20 минут» — опциональная интеграция CalendarContract.Instances с runtime READ_CALENDAR. Пользователь выбирает календари и возможность показать название. Читать небольшой временной диапазон, реагировать на ContentObserver, ничего не загружать самостоятельно из Google. Повторения/часовые пояса делегировать Calendar Provider. [Calendar Provider](https://developer.android.com/identity/providers/calendar-provider).

### 7. Фото, заметка и QR

Фото уже работает. Можно добавить локальную подпись «На встрече до 16:00», крупный QR выбранного пользователем контакта/ссылки или записки — удобно показать другой стороне при раскрытом телефоне. Это наша продуктовая идея, а не перенос функции Xiaomi17Pro. Источник — собственный текст/импорт, без автоматического чтения чужих приложений. QR требует отдельного генератора и проверки чтения камерой через реальные вырезы/масштаб; никаких сетевых запросов. Питомец, фото и карточка выбираются независимыми слоями, чтобы пользователь не терял фото при включении статуса.

### 8. Погода

В первой версии сохранить честный ручной режим дождя; не выдавать его за реальные данные. Для online-опции пользователь выбирает город/координаты, приложение делает HTTPS-запрос Open-Meteo с current temperature_2m, weather_code, precipitation; INTERNET — normal permission, сейчас отсутствует. Current у сервиса — модельная оценка, а не датчик телефона. Результат сохраняется с временем данных и временем загрузки; при ошибке показывать возраст кэша. [Open-Meteo Forecast API](https://open-meteo.com/en/docs).

Для личного некоммерческого приложения free API не требует ключа; условия сервиса ограничивают использование и требуют атрибуции данных CC BY4.0. Коммерческий выпуск нужно оценивать отдельно. Предложенная частота 30–60 минут при видимой панели с кэшем значительно ниже лимитов, не требует GPS или фоновой ежеминутной службы. Настройки объясняют передачу выбранных координат провайдеру. [Open-Meteo README](https://github.com/open-meteo/open-meteo), [условия](https://open-meteo.com/en/terms).

## Как сохранить низкий расход

Это проектные требования, а не уже проведённые измерения новых карточек:

- Одна активная карточка или компактная статусная строка; пользователь включает нужные блоки отдельно.
- Перерисовывать только изменившийся текст/иконку. Фиксированный фон не должен запускать декодер питомца.
- Подписки обычных статусов живут только пока панель видима; удалить callbacks и освободить обложки при stop. NotificationListener остаётся системным listener и не содержит frame-loop.
- Для часов минутная граница, таймера/медиа — 1 Hz только когда это видимые цифры. Никаких `dumpsys` на каждом тике и непрерывного Bluetooth scan.
- У скрытой панели ноль таймеров рендера/декодирования. Фоновый сигнал таймера — один AlarmManager deadline.
- Шрифты/иконки/обложки кешировать с пределом размера; bitmap для обложки порядка 256–512 px, не полный original.
- Обычный режим cards не держит wake lock и не отменяет системный сон. Отдельный режим «держать во время таймера» возможен только по явному выбору.
- Доступы запрашиваются при включении функции; их отказ показывает пустое/неактивное состояние, не ломает питомца и фото. Штатный сложенный интерфейс сохраняется.

## Что брать следующим

1. **Карточка батареи/заряда.** Небольшое расширение уже читаемых данных, не требует новых runtime-доступов; легко проверить кабелем и реальным battery broadcast.
2. **Медиакарточка.** Наибольшая польза с минимальным добавлением доступов: listener уже включён, MediaSession уже используется. Стартовать с play/pause/next и обложки; сложный seek позже.
3. **Видимый секундомер и фокус.** Самодостаточная локальная функция без сервера. Надёжный звук/уведомление в фоне добавлять отдельным этапом с alarm-доступом и lifecycle-тестами.

Network/VPN и приватные счётчики — следующая очередь. Online-погода, hotspot-контроль, календарь и QR — опции после стабильной основы, поскольку добавляют зависимости, доступы или OEM-неопределённость.

## Тесты перед обещанием поддержки

| Блок | Без реального телефона | На MIX Flip / HyperOS |
|---|---|---|
| Батарея | Модель: неизвестные значения, status/plugged, проценты, отсутствие property | Подключить/отключить кабель, сравнить ОС; не путать отладочный mock с физическим зарядом |
| Медиа | Test MediaSession: смена metadata/actions, pause, next, session destroyed, две сессии | Реальные установленные плееры, переключение устройства вывода, touch на внешней панели |
| Таймер | Внедряемые часы: пауза/сон/восстановление/смена wall-clock/новый boot id | Экран выключен, складывание, process kill, отсутствие alarm/notification-доступа |
| Уведомления | Дубли, groups, removed, reconnect snapshot, запрет источника | Собственное тестовое уведомление; удаление, lock/unlock, штатная privacy-редакция |
| Сеть/BT | Состояния callback, отсутствие permissions/profiles | Wi-Fi/мобильная сеть/VPN с split tunneling; реальные наушники, отключение |
| Геометрия | Обе ориентации, cutout слева/справа, большой font scale | Кнопки физически доступны вне камер, после складывания сохраняют место |
| Расход | Проверить отсутствие scheduling при stop и bounded caches | Сравнить статичный фон без карточки/с карточкой, playing/paused, visible/hidden, 20 циклов. CPU процесса, PSS, callbacks — одинаковые интервалы, минимум несколько повторов |

На этапе исследования код не менялся и телефон не использовался. Ссылки — первичная документация; возможность API не равна физической проверке конкретной HyperOS. После отдельного разрешения пользователя добавлена реализация ниже.


## Реализация после исследования

Добавлены optional rootless карточки, выключенные по умолчанию (`utilityCard=none`). Каталог оригинальных сцен и ресурсы Xiaomi не изменяются: это один дополнительный слой в PetStage, поверх PAG, MP4 или композиции/фото. Карточка находится справа внизу; камера резервируется по insets с fallback34% ширины. Preview не резервирует область камеры и использует компактный таймер; кнопки остаются не ниже 48dp.

- **Батарея:** процент, статус заряда, тип питания и температура батареи; данные sticky ACTION_BATTERY_CHANGED, без shell или background polling.
- **Медиа:** название/исполнитель и play/pause/next через опубликованную MediaSession; неподдерживаемые действия отключены. Смена metadata/actions отслеживается callbacks. Обложка и seek не реализованы. Дополнительных разрешений нет — используется существующий доступ к уведомлениям. Названия треков в AppLog не записываются.
- **Визуальный таймер:** секундомер и 25 минут фокуса, старт/пауза/сброс. Монотонные часы учитывают сон; prefs пишутся при действиях, скрытии и завершении, не каждую секунду. После нового/неизвестного boot приостанавливается на сохранённом checkpoint. Пока панель скрыта процессу не нужно тикать: при возвращении значение вычисляется заново. Звука и точного фонового будильника нет, что явно указано в интерфейсе.

Settings entry point: `UtilitySettings.populate(Activity, LinearLayout, PetStage)`. Он добавляет выбор карточки и два режима таймера; родительская задача интегрирует этот вызов в MainActivity. UtilityCardView управляет своим lifecycle через PetStage.start/stop; остановка снимает listeners и handler callbacks. Настройки карточек общие для обеих панелей и меняются сразу.

Сначала Java-компиляция исходников проверена с Android36 SDK. Затем собран APK0.7; на стандартном Android16 в эмуляторе прошли 15 runtime-проверок карточек, включая реальные callbacks тестовой MediaSession, timer UI и восстановление настроек. Это эмуляторная проверка, не проверка HyperOS/телефона. TimerStateTest прошёл **24 проверки**: сон, пауза/возобновление, сохранение и та же загрузка, другая/неизвестная загрузка, неверная монотонная отметка, точное завершение фокуса, отсутствие повторного завершения, restart/reset, fallback повреждённого режима. Эти 24 проверки не заменяют ранее проведённые проверки ресурсов и не увеличивают объявленный результат устройства.

Аппаратная проверка новых карточек ещё требуется: touch и вырезы камер, высота при увеличенном шрифте, реальные плееры, отзыв notification-доступа, battery broadcasts, восстановление после складывания/сна/перезагрузки, CPU и PSS отдельно для visible/hidden. Телефон вновь подключён; ограниченный отчёт0.7 подтверждает установленный APK, Shizuku UID2000, state5/два экрана, foreground service и регистрацию реального hinge-angle sensor. Новые карточки0.7 физически ещё не подтверждены. APK0.7 собран и связан с актуальными эмуляторными результатами SHA-256: 59668c8a20c7833d70ee1bc944b928faa14eb494ee590eadc24ddabb0ee191d4.

Уведомления-счётчики, network/Bluetooth/hotspot, будильник/календарь, QR, online-погода и точный background alarm остаются предложениями, а не реализованными возможностями. Карточки не добавляются в PetWallpaper: первый этап предназначен для отдельной внешней панели и main preview.

Utility в 0.7 остаются опциональными дополнениями; наличие MediaSession API не доказывает, что их внешний вид повторяет 17 Pro. Ниже — возможности, подтверждённые конкретными донорскими MAML, а не придуманный список виджетов.

Погодные binder URI (`content://weather/weatherData/4/...`) и календарные festival-provider URI видны в исходных MAML, но их экспорт/разрешения/схема в EEA не подтверждены. На следующем подключении можно проверить manifest/provider read-only. Если доступ запрещён, не подставлять выдуманную «погоду Xiaomi» и не считать Shizuku универсальным обходом signature-permissions.

Наиболее полезная следующая тройка: **нативное приветствие/переходы Roe/Bubbles → локальная очередь Lumi/Peeko → исходные часы/12–24ч и текстовые слои**. Она приближает порт к донорской логике без новых сетевых служб. Перед отдельным видимым медиавиджетом/зарядной заставкой нужно найти именно соответствующие layout/drawable/код системного rear-screen сервиса; скрытый MusicControl и battery-переменные питомца их внешнего вида не доказывают.

Из ресурса следует заданный fps/режим воспроизведения, но не измеренная эффективность системы Xiaomi. Производительность этих переносов нужно сравнивать на той же сцене и устройстве; бренд/OEM или frameRate=0 в отдельных MAML не служат доказательством низкого расхода всех сценариев.
