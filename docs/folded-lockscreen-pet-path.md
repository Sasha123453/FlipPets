# Питомец на штатной блокировке сложенного MIX Flip

Исследование 11 октября 2026. Только анализ локальных APK/DEX и документации;
телефон не подключался, приложение и настройки не менялись. Этот документ
уточняет именно **folded + locked**, отдельно от карточек после разблокировки.

## Вывод

Предпочтительный путь — добавить наш подготовленный PAG как пользовательский
шаблон в существующую систему `ai_pets` MIX Flip:

```text
Flip Pets: PAG + точный постер + геометрия + TemplateItem
        ↓
Штатный редактор com.miui.aod
        ↓ подтверждение пользователя, штатное копирование ресурсов
current_tiny_keyguard_info + all_tiny_keyguard_info
        ↓ штатное наблюдение за настройками
SystemUI: TinyKeyguard → AiPetsTemplateView → AiPetsPagView
```

Это не Activity поверх блокировки, не режим FlipHome и не перенос SystemUI с
18 Pro. MIX Flip уже содержит нужный класс в собственной внешней блокировке.
Название `ai_pets` здесь обозначает формат шаблона: готовому донорскому PAG не
нужен генератор или доступ к серверу Xiaomi.

Возможность пользовательской установки пока не доказана на телефоне. Xiaomi
[официально описывает](https://www.mi.com/uk/support/faq/details/KA-485441/)
анимированных встроенных питомцев внешней блокировки, но не поддерживает
произвольные динамические обои в обычном пользовательском сценарии. Наш путь
использует найденный внутренний редактор, поэтому требует отдельной проверки.

## Что найдено дополнительно к прежнему анализу редактора

Ранее была прослежена загрузка в редакторе AOD. Теперь проверена сторона
**реального SystemUI**, которая показывает уже выбранный шаблон.

Локальный SystemUI: Global `ruyi OS3.0.303.0.WNIMIXM`, SHA-256
`bbb73370372d95707caa07bc00a6b2674afc5f433e5b074c4f8d6837b74ba757`.
Его совпадение с фактическим EEA SystemUI ещё не проверялось. Исторический AOD
был получен с EEA; текущую версию на телефоне надо подтвердить заново.

Исходники исследования лежат в игнорируемом
`work/folded-research/folded-lock-audit/`.

| Класс | Подтверждённая роль |
|---|---|
| `TinyTemplateViewFactory` | Отображает ID `ai_pets` в `AiPetsTemplateView` |
| `TinyKeyguardPanelViewControllerImpl` | Читает и наблюдает `current_tiny_keyguard_info` / `all_tiny_keyguard_info`; передаёт пробуждение/сон текущему внешнему шаблону |
| `AiPetsTemplateView.bindPetsPagViewData` | Берёт `resourcePag` из шаблона, задаёт путь и геометрию `AiPetsPagView` |
| `PetsTemplateView.startWakingUp` | Управляет проигрыванием при пробуждении, учитывая уведомления и биометрическое разблокирование |
| `AiPetsTemplateView.handleSingleClick` | Может повторно запустить анимацию по касанию |

Хэши, ограничения декомпиляции и сводка:

## Каким будет поведение

По исследованному коду это **короткая штатная анимация на активной блокировке**,
а не непрерывный питомец при погасшем экране:

- Первичная привязка AI-шаблона вызывает `init(..., false, false)`: сама загрузка
  шаблона не равна запуску движения.
- При пробуждении родительский `PetsTemplateView` может запустить PAG. Наличие
  уведомлений подавляет эту ветку проигрывания; биометрическое разблокирование
  также может пропустить её. Это нужно включить в тестовую матрицу.
- Касание вызывает повтор при подходящем состоянии проигрывателя. В ветке
  перехода к AOD обработка касания не выполняется.
- После конца AI-анимации слой PAG плавно скрывается за 450 мс и сбрасывается к
  кадру 0. Поэтому неподвижный постер между проигрываниями может быть штатным.
- Складывание само по себе не доказывает запуск: `onFlipFold` переводит PAG в
  неподвижное состояние, а AI-подкласс скрывает его слой. Пробуждение — отдельный
  триггер.
- При переходе ко сну проигрывание ставится на паузу. Сохраняем родной AOD,
  уведомления, PIN/биометрию и нормальный таймаут.

Это статическая модель поведения, не запись опыта на EEA телефоне. При проверке
нужно отдельно наблюдать фон/постер и реальные меняющиеся пиксели питомца.

## Важное уточнение геометрии

В SystemUI у `AiPetsTemplateView` есть две ветки:

1. Если у обеих ориентаций есть `wallpaperInfo.positionInfo`, позиция PAG берётся
   из отрицательных `left/top` этих структур.
2. Иначе используется запасной путь с координатами первого кадра.

Следовательно, правка только `firstFrameCoordinateAxes` может вообще не изменить
положение уже оформленного шаблона. Надо сверять JSON, который получился **после
редактора**, с тем, что читает SystemUI. Настройка положения в редакторе может
изменить предпочтительную ветку. Масштаб из нашего `CoverGeometry` сюда не
переносится автоматически.

Для Charlie уже подготовлен неизменённый PAG 976×596 и точный декодированный
постер. Восемь образцов кадров полезны для доказательства декодирования, но не
покрывают весь контур движения. Проверять две ориентации, полную анимацию,
физические камеры и место для часов. Исходное обрезание хохолка остаётся.

## Варианты установки

### A. Штатный редактор без root — первый выбор

Использовать уже найденный exported-редактор:

```text
package: com.miui.aod
activity: com.miui.tinykeyguard.editor.edit.EditActivity
action: miui.tinykeyguard.editor.EDIT
string extra: param_template_item_json
clockInfo.templateId: ai_pets
pets.petCategory: 2
```

Подготовить отдельный `bizId`, обычные читаемые файловые пути к PAG/постеру и
валидный `TemplateItem`. `content://` пока не является подтверждённым форматом
для этого пути: стандартного URI-grant недостаточно, если код ожидает `File`.
Не расширять глобальные права доступа. Проверить читаемость подготовленного
ресурса под UID редактора и факт нативного PAG load.

Исторический preview уже принял JSON и показал Charlie, но движение не было
подтверждено. Теперь нужно повторить именно проверку движения с точным постером,
не считать статичную картинку успехом.

В `TemplateApiImpl.applyTemplate` видна последовательность: `fileCopy`, запись
текущего шаблона, затем опциональное добавление истории. Копирование делает
штатное приложение со своими правами. Поэтому отказ shell на запись в native
каталог не означает, что обязательно нужен root.

### B. Root как помощник установки/отката — запасной путь

Если без root нельзя надёжно прочитать предыдущие ресурсы, подготовить входные
файлы или восстановить состояние, KernelSU может дать узкий помощник для этих
операций. Рендеринг всё равно должен выполнять штатный SystemUI.

Нужны точные профили APK/прошивки, разрешённые пути, проверка хэшей и владельцев,
журнал собственной транзакции и восстановление после обрыва. Предпочесть
штатную запись/уведомления кэша прямой подмене настроек. Нельзя считать простую
запись JSON и файла законченной установкой. Не ставить SystemUI/AOD от 18 Pro,
не заменять встроенного питомца в его слоте и не отключать SELinux.

Хуки в SystemUI пока не нужны: найденный класс уже принимает путь к PAG. К ним
возвращаться только при доказанном конкретном ограничении штатного пути.

## Что выяснилось об откате

`rollbackAiPetsByBizId` — **не точное восстановление**. Он фильтрует историю по
`bizId`, может выбрать первый оставшийся шаблон, а после обновления истории
удалить ресурсы отфильтрованных записей. Если не осталось записей, выполняется
другая очистка. Это не гарантирует возврат к точному прежнему оформлению.

Кроме того, `createHistoryItem` ограничивает прежний список девятью записями перед
возможной вставкой новой. Нужно учитывать изменение порядка и вытеснение истории,
а не сохранять только `current_tiny_keyguard_info`.

Найден `TinyKeyguardBackupDelegate`: он сохраняет данные текущего шаблона/истории
и архив native-ресурсов; восстановление содержит проверку и преобразование
шаблонов. Это внутренняя связка с `FullBackupAgent`, **не готовый публичный API**
отката нашего приложения. Она полезна как перечень зависимостей. Декомпиляция
этого класса сообщила 40 ошибок; сложные ветки требуют проверки по DEX.

Перед Apply надо установить:

- Какие точные настройки, ресурсы обеих ориентаций, предпросмотры и native
  wallpaper-состояния меняются, включая побочные действия редактора.
- Как сохранить предыдущие байты и метаданные без копирования живой общей БД.
- Как восстановить их с правильным обновлением штатного состояния/кэша.
- Как пережить прерывание между копированием, текущим выбором и историей.
- Как не перезаписать более поздний ручной выбор пользователя и не удалить ещё
  используемые ресурсы.

Обычное повторное применение старого шаблона может восстановить вид, но не всю
историю и метаданные. Это отдельные уровни результата; не смешивать их.

## Следующие действия для агента

**Без телефона можно продолжать:**

1. Подготовить отдельный генератор/валидатор JSON `TemplateItem` для готового
   Charlie и manifest ресурсов. Генерация здесь — сериализация, не AI.
2. Проследить обе геометрические ветки и данные после editor crop; добавить
   проверки координат для 0/180°. Не выдумывать физическую безопасную область.
3. Составить карту native Apply: копии файлов, preview/wallpaper side effects,
   secure settings и история. Сомнительные coroutine-ветки сверять с DEX.
4. Спроектировать receipt/rollback и протестировать прерывания на файловой
   модели. Это подтверждает наш алгоритм, но не доступы или кэши HyperOS.
5. Добавить в будущий read-only capture также `com.android.systemui`, поскольку
   совпадения AOD недостаточно для проверки настоящего экрана блокировки.

**Когда телефон станет доступен:** точные AOD/SystemUI хэши → читаемость staged
ресурса → preview с реальным движением → доказанный rollback → Apply → настоящая
сложенная блокировка. Проверить пробуждение без уведомлений и с ними, касание,
биометрический вход, Power/таймаут, поворот, складывание и перезагрузку.

Рекомендуемый первый результат — **один Charlie на штатной сложенной блокировке
с нормальными часами и обратимым применением**. После этого перенос остальных
совместимых PAG существенно проще. Отдельный питомец folded/unlocked не нужен:
там остаются штатный лаунчер и карточки.
